# CodeMe application review — 30 October 2026

The target is a reliable coding agent that runs on the user's machine, prepares a local model, inspects a project, proposes changes, and continues from approved execution and verification results. This review checked those transitions in the implementation and exercised both real Ollama inference and the native VS Code editor.

## Confirmed problems and fixes

| Area | What was wrong | What changed |
| --- | --- | --- |
| File application | Editor-buffer hashes could be reported as applied without explicitly saving the source to disk. | Changes are saved and checked against both editor content and disk bytes before success is recorded. |
| Line endings | Native VS Code normalized new CRLF text to the editor's default, despite passing the previous stub tests. | LF/CRLF is set explicitly in the same edit. Unrepresentable mixed/bare-CR proposals are refused before source mutation. |
| Failure recovery | A failed edit could blindly remove a concurrently created file or overwrite newer content during rollback. | Recovery checks the current buffer/disk state. Unexpected content and uncertain empty-file ownership are preserved with an actionable checkpoint error. |
| New folders | A create proposal failed whenever its parent folder did not already exist. | Approved create paths can create bounded, validated parents. Preview never writes them; restore removes only owned empty directories. |
| Read-before-edit | A partial read, a same-turn read request, or a compacted tool reply could authorize edits to source the model had not seen. | Permission uses text actually delivered in a later model request and its exact source hash. Whole-file replacement requires a complete bounded read. |
| Source accuracy | Universal newline conversion changed CRLF reads, breaking exact-text edits. | Reads preserve source line endings and expose the full source hash. Changed files require a fresh read. |
| Honest completion | Directory listing alone could justify an action task's “already done” outcome. | No-op completion requires actual source inspection rather than a listing alone. |
| Context budgets | Native tool definitions were missing from the budget; correction history could crowd out the original goal. | Tool schemas consume the budget explicitly. The original goal is preserved or the user receives an actionable context-limit error. |
| Local inference | An Ollama alias stayed trusted for a whole client/task after its first local-weight check. | Installed local-weight inventory is checked before each prompt, including later turns. |
| Model suitability | Chat readiness was treated as enough information for Agent mode. | Setup and an installed-model capability API distinguish supported, unsupported, and unknown tool support. Ask remains available for chat-only models. |
| Repair model | Verification could request the extension's missing configured model after setup had selected an installed alternative. | Task repairs keep the original task model; independent verification uses the backend's prepared default. |
| UI recovery | Stalled requests, outdated health/workspace responses, setup polling, and rejected Resume actions could leave confusing or locked state. | Requests/streams have bounded waits, newer state owns responses, Cancel can interrupt passive setup reads, and rejected Resume requests finish cleanly. |
| Drafts | Browser navigation or reload discarded unsent messages. | Bounded drafts are kept per backend and conversation for the browser session. |
| Launcher | Windows backend termination could skip cleanup; frontend/backend port conflicts were discovered after startup. | Owned services receive a graceful shutdown attempt and bounded fallback. Port conflicts are rejected early; reused services are not terminated. |
| Native testing | The old integration command pointed to an unbuilt test file and did not export the native test runner contract. | The harness runs an explicitly selected installed editor with isolated workspace/profile/extensions and no editor download. |
| Browser dependencies | The Angular 18 stack had 20 production audit findings, including critical/high advisories without an in-range framework fix. | Upgraded to Angular 21.2.25 LTS and CLI/build 21.2.29, TypeScript 5.9.3, and Zone.js 0.16.3. Both full and production frontend audits now report zero findings. |
| Unused server path | The legacy Node SSR server could listen beyond localhost and brought unused Express/SSR dependencies. | Removed SSR, prerendering, Express, unused Material/animation dependencies, and legacy Webpack tooling. The browser is static; development serving explicitly binds loopback. |
| Model evidence | A single live repair could hide failures in other coding tasks. | Added an opt-in installed-model evaluation matrix with exact source/evidence oracles, separate quality/recovery/policy results, transport metrics, provenance, and bounded requests. |
| Installation evidence | Existing environments could conceal missing dependencies or upgrade regressions. | Added a fresh-copy installer/build/launcher/upgrade harness with isolated user state, controlled model-protocol failures, offline relaunch, and a manual OS CI matrix. |
| Large repositories | Broad snapshots could crowd local context without explaining file relevance. | Added bounded task-ranked path/symbol/import hints, explicit partial-map notices, fresh results after changes, and optional context that yields to the original goal. Metadata never grants edit permission. |
| Recovery diagnostics | Invalid proposals returned a generic type error without naming the field, making correction difficult for local models. | Errors identify the operation and nested schema field with bounded messages while omitting invalid source values and arbitrary extra keys. |
| Windows restart evidence | A detached launcher stop could leave a virtualenv's backend child running, allowing the installation test to reuse an old server. | Console Ctrl+Break enters normal launcher cleanup; forced fallback targets the owned backend tree. The smoke now requires a closed backend port and distinct server identities across relaunch. |

## What the live checks establish

An existing local `qwen2.5-coder:7b` was warmed through the setup coordinator, answered a synthetic chat, read a temporary Python source file, proposed the correct `a - b` to `a + b` change, and paused for approval. The file remained unchanged and no command ran. No model weights were downloaded.

That installed model advertised tool support but returned tool JSON in assistant content during the synthetic call. CodeMe's existing structured-content compatibility parser handled the actual coding task. Advertised capability is a compatibility hint, not proof of native-call quality or performance on larger projects.

The native extension checks passed on VS Code 1.144.0: activation; saved modify/create operations with nested folders, Unicode, LF and CRLF; guarded restore; unsaved-buffer conflicts; and refusal to report success after a real save hook changed the approved content. Test-only state stayed in an isolated workspace/profile. No operating-system security settings were changed.

A separate real-model verification/repair test also passed: an actual pytest failure was sent to local Qwen, its repair paused for explicit fixture approval, the approved edit was applied, the unchanged verification plan passed, and restore reproduced the original source hash. This test used real HTTP, SQLite, local inference, and controlled process execution. Its editor adapter was the test stub; the native editor behavior was covered separately above. All execution and temporary data belonged to disposable fixtures.

Cold hardware discovery exceeded a short readiness probe on this machine. The setup coordinator now allows a bounded minute for an installed daemon to become ready, with a visible startup message and cancellation checks; model loading keeps its separate timeout.

It reused downloaded pip/npm archives, then ran the actual installer, built the browser, launched the API and SPA, exercised controlled model reuse/retry/cancellation/load failures, preserved a fixture conversation and user configuration through an offline dependency upgrade, and relaunched successfully. The two backend identities differed; both launchers exited successfully and both backend ports closed. The final privacy-only harness change was checked in a separate source snapshot, with production source identical to the installed copy.

This was a fresh-copy test on an existing Windows host, using a controlled loopback model server. It did not install an OS runtime, download model weights, or prove a clean OS/GPU installation. Python 3.10.11 and Node 24.14.1 were used. Reports are under `.runtime/install-smoke-52au63dk/`, including `report.json` and `source-validation.json`. The manual Windows/macOS/Linux workflow is configured but has not been dispatched as part of this local review.

Three manual navigation queries against CodeMe itself placed `model_setup.py`, `codeme_cli.py`, and the extension's `changeSetManager.ts` first for their respective tasks. The save query initially missed the editor implementation; unique term coverage and sampled term rarity corrected that gap. The final checks took approximately 390–485 ms on this host, with source parsing below the 512 KiB cap. These are navigation checks, not model task-success or general performance benchmarks; partial-map notices remain visible. Before/after artifacts are under `.runtime/priority-repository-selection*.json`.

The final suite-version-2 live evaluation used the only installed model, `qwen2.5-coder:7b`, after installation/build/tests had stopped. It passed **5/6 model-quality cases, 1/1 injected recovery case, and 2/2 policy controls**, with no transport/oracle errors or skipped cases. Passing quality cases covered a simple repair, nested creation, source facts, scoped guidance, and finding/repairing a deep implementation among 128 distractors. The multi-file case failed: the model returned prose without the required reads or proposal, and the controller blocked it rather than claiming success. The CLI correctly returned a failing result for that incomplete task.

All fixture bytes remained unchanged; no action was applied, project command executed, or model downloaded. There were 20 actual model requests, zero native tool calls and 16 tool calls recovered from assistant content. The context setting was 8,192; request/case/matrix limits were 120/180/1,800 seconds with six requests per case. Sampling defaults remained server-owned and are recorded as unspecified. The matrix took about 201 seconds excluding runtime warmup, then unloaded the owned model and stopped its daemon. This is one run on one model, not a general reliability or speed claim. Earlier suite/source versions and runs with competing workload are preserved separately and should not be used as a controlled before/after comparison.

The final JSON report is `.runtime/evaluations/qwen2.5-coder-7b-suite-v2.json`. ## Validation and upgrade notes

- Browser: 46 tests and the static production build passed on Angular 21. The initial bundle fell from about 587 KB to 524 KB. The existing bundle-budget and Prism CommonJS warnings remain.
- Extension: 102 Vitest tests and typecheck/build/package passed; two other opt-in suites remain excluded from the ordinary unit command. Native editor checks and the real-model repair test above were run separately.
- Backend: 479 tests passed in the final integrated suite, including evaluation, installation-isolation, repository-selection, proposal-recovery, and launcher regressions. XML and detailed logs are under `.runtime/`; tests use temporary databases and ordinary tests cannot start real model downloads. The existing Starlette/httpx test-client deprecation warning remains.
- Launcher: the rebuilt browser bundle, a direct SPA route, and the generated backend runtime URL were served by the real launcher against a disposable database. Automatic setup opt-out was respected and the owned backend shut down gracefully.
- Dependencies: frontend full and production audits report zero findings; extension production audit reports zero. Python `pip check` reports a consistent environment. These are installed-version/advisory checks, not a claim that every dependency or future release is risk-free.

The browser dependency set fell from 945 to 544 packages. First installation/development now needs Node.js 20.19+, 22.12+, or 24.x within those supported majors; Node.js 24 LTS is recommended. Existing installations should stop CodeMe and rerun `python install.py` to install the updated lockfile and rebuild the browser. Existing configuration, database and model weights are preserved. Repackage/reinstall the extension for its editor fixes.

The unused Node SSR command is intentionally gone. `python start.py` still serves `frontend/dist/frontend/browser` with local single-page routing; no Node runtime is needed for later serving of that existing build.

## Remaining gaps, in practical order

The later catalog/branding/repository follow-up passed **521 backend tests**, **64 browser tests**, **109 extension tests**, and **15 packaging tests** (the packaging tests are included in the backend total). Both clients built successfully; the VSIX and private customer ZIP include the current logos and applicable license notices. Repository identity, versions, icons, maintained-document links and YAML configuration were checked separately. GitHub About description, homepage and topics were applied and read back successfully. New CI workflows are configured; local test results alone do not claim a successful remote CI run. The ₹499 Cashfree product and protected website download remain unpublished.

1. **More models and better task reliability.** The repeatable suite now covers small repairs, multi-file edits, nested creation, source explanations, scoped guidance, noisy repositories, recovery and controls. Real coverage still depends on installed models and hardware. Capability metadata and passing policy controls cannot establish coding quality; failed tasks must remain visible in reports.
2. **Clean-OS and real-runtime installation evidence.** Fresh-copy checks exercise actual dependency installation, launch, controlled setup failures and upgrade preservation. The configured Windows/macOS/Linux workflow still needs actual dispatch results; representative clean machines must also test OS runtime installation, GPU discovery, and interrupted real model downloads.
3. **More precise context and continuity.** Fresh bounded navigation is implemented. Budgets remain conservative character estimates; tokenizer-aware compaction, representative large-repository quality measurements, and incremental local indexing remain future work.
4. **Browser Agent features.** The browser remains a chat and read-only explorer. Reviewed editing, process execution, checkpoints, and verification belong to the extension; browser parity needs an explicit execution design.
5. **Operational limits and retention.** The backend still requires one worker. Request-body limits, backup/checkpoint retention, and larger-history performance deserve dedicated work.

Approvals, canonical results, and current-file verification remain required. The review improves CodeMe's implementation; it does not establish identical intelligence or feature parity with Codex, or prove every project script safe to run.
